## [Unreleased]

### Added
- **Every downstream sidecar and the consolidated run manifest name their run too.** The four `womblex.*` run keys now land on all seventeen per-batch sidecar writers — chunks, normalised text, spellfix text and corrections, the three enrichment sidecars plus the persisted Document, the graph-refresh rewrites, embeddings, money spans and columns, entity links, PII spans and clean text, and chunk quality — and on `<run>/manifest.parquet`. A stage does **not** declare its own stamp: it inherits the run from a stamped sibling of the batch its sidecar sits beside (`stamp_for_sidecar` prefers `<base>.elements.parquet`, then the manifest, then any sibling — every file of one run carries the same run id and digest), and the consolidated manifest reads it back from the per-batch manifests. The fallback is load-bearing rather than defensive: a stage worker stages in only the inputs its contract declares, and `embed`, `link`, `pii`, `quality` and `graph-refresh` do not declare the elements shard — insisting on it would have left exactly those five unstamped on a worker and stamped locally. This is the only trustworthy source — a stage is handed a shard directory, not a run, and its own `dataset.run_id` is whatever config it was launched with, so a copied config would have it stamp a run it did not produce. It is also what makes the local and distributed stamps match by construction rather than by both invocations happening to be handed the same YAML. `run_id` and `config_digest` are inherited because they describe the *run*; `version` is the running `__version__` because it describes the *bytes*, so a stage run at a later build says so instead of repeating what extraction claimed. An unstamped or absent base shard yields an unstamped sidecar, and batches naming two runs leave the run keys off the consolidated manifest — the rule the ingest-root footer already follows for a mixed-root directory. `tests/test_run_stamp_sidecars.py` is the acceptance criterion's enumeration test: it walks every public writer in `womblex.store` and fails on one that is neither stamped nor in an exempt list that carries a reason per entry (the extraction writer, which takes its stamp explicitly; the JSON feedback record; the standalone register ingests and the pre-extracted records ingest, which are not runs; and the three whole-corpus E2E enrichment writers, which have no per-batch shard to inherit from — their only caller, `operations.write_batch_enrichment`, has had no caller of its own since in-batch enrichment was removed in 0.5.10, and is a fossil worth retiring separately). Completes the provenance-chain link "run to output", and is what P9's stage inventory reads: a stage that ran is now observable from the stamps rather than declared from a config flag. Footer metadata stays additive, so no reader changes.
- **Every extraction Parquet names the run that produced it.** New `store/run_stamp.py` stamps four namespaced footer keys — `womblex.run_id`, `womblex.version`, `womblex.config_digest`, `womblex.stage` — onto all four shard files, so a shard copied out of its run directory still says which run it belongs to and a file mixed in from another run is distinguishable from a native one. Previously the run id existed only as a directory name and was lost the moment a shard moved. `RunStamp` is declared once per run and re-pointed at each writer (`for_stage`), so the run id, version and digest cannot drift between one run's files; the caller supplies it for the same reason it supplies `IngestProvenance` — only the caller knows the run id — and an omitted stamp writes no run keys rather than inventing one. The digest is over the *validated* configuration (pydantic defaults and the AI-chunking validator both rewrite what the YAML supplied), so two YAML files differing only in formatting produce one digest; `paths` and `dataset.run_id` are excluded, the first because where a deployment keeps its files is not what the pipeline does — that exclusion is what makes a worker's stamp match the local run's for the same config and corpus — and the second because it is stamped in its own right. Wired at the two run entry points (`womblex run` and `cloud/worker.py`, both via `process_batch`); the one-off `womblex extract <file>` and the back-compat E2E chunk path stay unstamped, being no run, and a queue row naming no run publishes unstamped on the same terms an undeclared ingest root already gets — a malformed row costs the stamp, not the batch's extraction. Footer metadata is additive, so readers are unaffected. First half of the provenance-chain link "run to output"; the second half is the entry above it.
- **Manifest and Parquet footers record where the source document came from.** `MANIFEST_SCHEMA` gains `ingest_root` (scheme-qualified: `file:///srv/corpus`, `s3://bucket/inbox`) and `source_relpath` (the path under it), so root + relpath names the document and a corpus that moves to a new root re-resolves without a rewrite; `collection_id` is populated rather than left empty. The same pair is stamped into every extraction Parquet's footer key-value metadata under `womblex.*` keys, reusing the namespacing convention `store/register_manifest.py` already reads back from the register ingests, so a shard copied out of its run still names its corpus. New `store/source_provenance.py` holds root qualification, relative-path resolution and the footer keys; the root is declared by `paths.ingest_root` (new, optional) or `paths.input_root`, or by the enqueue invocation for a distributed run — never inferred from the working directory. Shards written before the columns read back with them empty (`_MANIFEST_BACKFILL`), and footer metadata is additive, so existing readers are unaffected. Masking is a stated non-goal: a `pii` run over a completed run leaves the manifest byte-identical.

### Removed
- **The `security` and `Secret scan (history)` CI jobs.** `.github/workflows/ci.yml` now runs `test` and `Console frontend (ui/)` only. This takes CI's semgrep SAST (Python + OWASP + the local rulesets, blocking), the informational `pip-audit` dependency audit, the whole-tree detect-secrets pass and the KeyHog working-tree + reachable-history scans out of the pipeline; nothing checks a pushed commit for credentials or injection sinks any more. The commit-time hooks in `.pre-commit-config.yaml` still run detect-secrets and the local semgrep rulesets, so the pragmas and `.secrets.baseline` below still do their job — but they are opt-in per clone (`pre-commit install`) and `--no-verify` walks past them, where CI could not be skipped. `.semgrep/rules/`, `.secrets.baseline` and `.keyhogignore` are retained, so restoring the jobs is a revert of this commit.

### Fixed
- **The secret scan passes.** It has failed on every run since the scanner landed: `.secrets.baseline` was generated in the same commit that added `docker-compose.local.override.yml` and the storage-options credential tests, and `detect-secrets scan` walks files git already knows about — so the baseline never covered the four sites that same commit introduced, and both the `security` and `Secret scan (history)` jobs went red immediately and stayed there. Fixed at the sites, per the convention in CLAUDE.md and README: an inline `# pragma: allowlist secret` with a reason on the bundled-local Postgres DSN and MinIO default in the override compose file, and on the three fake-credential assertions in `tests/test_cloud.py` (the same literal appears twice in one test, and both occurrences need one). A pragma travels with the line where a baseline entry goes stale as soon as the file is edited — which is the second failure behind the first: the baseline's `docker-compose.yml` line numbers had drifted, so the hook rewrote the file and exited non-zero even once no secret was reported. Those line numbers are refreshed here, and the regeneration trap is recorded beside the command in `.pre-commit-config.yaml`.
- **Two documents whose store keys share a basename are both extracted.** A worker staged its batch's documents into one flat scratch dir, so `2026-07/report.pdf` and `2026-08/report.pdf` — routine under a dated or per-agency upload layout, which `list_files(recursive=True)` has enumerated since the ingest-listing fix — landed on one local file: the second won, one document was extracted twice and one not at all, and the recorded ingest provenance was the survivor's. `RemoteStore.download_to_dir` gains `nested=`, which mirrors each key's prefix under the staging dir, and `cloud/worker.py` stages documents that way. A key is canonicalised and asserted to stay under the staging directory before anything is written to it, so a `../` in a queue row cannot escape the scratch dir. Staging stays flat everywhere else — the shard, manifest and checkpoint callers pull siblings of one prefix into the flat directory the `*_shards()` entry points and readers expect — and the collision warning is retained there.

### Changed
- **`normalise`, `pii`, `quality` and `enrichment_doc` write through the shared row writer.** Each had its own copy of the same build-table-then-`pq.write_table` body that `store/output.py`'s `_write_rows` already holds (and that `money`, `spellfix`, `embed` and `entity_links` already call); stamping them would have added a fifth and sixth copy of it. Byte-identical output — same zstd level, same empty-but-schema-correct file — with the footer applied in one place. `_write_enrichment_rows` keeps its own body, which now takes the metadata through.
- **The link and embed stage sidecars moved out of `store/output.py` into their own modules.** `store/entity_links_output.py` and `store/embed_output.py` now hold the `*.entity_links.parquet` and `*.embeddings.parquet` schemas, path conventions and readers/writers, matching the one-module-per-stage-sidecar shape `store/pii_output.py`, `store/money_output.py`, `store/normalise_output.py` and `store/spellfix_output.py` already follow. `store/output.py` is the *extraction* writer, a different concern, and carrying two downstream sidecars had taken it past the 750-line file cap. A pure move: no schema, filename or behaviour changed, and import sites were updated rather than shimmed, so there is no second name for anything.

## [0.5.12] - 2026-08-25
Patch. Local model artefacts resolve per artefact across every models
root, so `WOMBLEX_MODELS_DIR` no longer shadows the wheel-bundled en_AU
dictionary and kanon-2 tokeniser; `spellfix` fails loudly on an unresolved
dictionary; a stage job blocked only on a not-yet-produced upstream input
is released rather than failed; and `spellfix` leaves the `DEFAULT-Isaacus`
reference shape. No parquet schema changed.

### Changed
- **`spellfix` dropped from the `DEFAULT-Isaacus` reference shape.** The reference pipeline is now `extract → normalise → enrich → chunk → build_graph → embed → money → link → done`, with `processing.text_source: normalised`. Dictionary-gated OCR repair rewrites source text on a dictionary judgement, and Australian government documents are dense with proper nouns, statute short titles and agency acronyms that are legitimately out-of-dictionary — that is a per-corpus call to make after measuring, not a reference default. The stage, its config section, its CLI command and its place in `PIPELINE_ORDER` are all unchanged and still reachable (`spellfix: {enabled: true}` plus `text_source: spellfix`); only the default composition changed. Config, preset overlay (`ui/presets.py`) and README's per-stage sequence (now 9 steps) edited together; `test_config_file_and_ui_preset_agree` pins that neither carries it.

### Fixed
- **Local model artefacts resolve per artefact across every root, so `WOMBLEX_MODELS_DIR` no longer shadows the wheel-bundled ones.** `utils/models.py` returned a single directory (`find_models_dir`) and looked only there, but the roots hold different artefacts: a container image mounts the large ones at `WOMBLEX_MODELS_DIR=/app/models` while the small ones (`en_AU`, `kanon-2-tokenizer`) ship inside the wheel under `womblex/_models/`. Setting the override therefore made `resolve_local_model_path("en_AU")` return the bare string and the `spellfix` stage die inside spylls on the relative path `en_AU/index.aff`. The new `model_roots()` enumerates every existing root in priority order and `resolve_local_model_path` returns the first that actually holds the named artefact — the override supplements the bundled root rather than replacing it. `find_models_dir()` is retained (highest-priority root) but must not be used to build an artefact path. Both Dockerfiles' comments corrected to match. Pinned by `tests/test_models_resolution.py`, which covers the exact image scenario (override root lacking `en_AU`) alongside the HF `snapshots/<hash>/` and bare-`.pt` behaviours.
- **`spellfix` fails loudly when its dictionary cannot be resolved.** A bundled-only Hunspell dictionary has no remote fallback, but `_dictionary` turned the resolver's "not found" bare string into the relative path `en_AU/index` and surfaced as `FileNotFoundError: 'en_AU/index.aff'` several frames inside spylls. It now raises a `FileNotFoundError` naming the artefact, the roots searched, and where the dictionary is meant to ship.
- **A stage job blocked purely on a not-yet-produced upstream input is released, not failed.** A stage whose every base raised `NotReady` exited non-zero, which `cloud/worker.py` recorded via `queue.fail` — so a stage claimed ahead of its upstream spent an attempt per poll and, on a slow-draining run, landed terminally failed for a pipeline that was merely early. `_run_stage` now distinguishes the all-blocked case as `StageNotReady`, and the worker loop `release`s it (attempt not consumed, reason recorded, backs off by `poll_interval`) exactly as it already did for the ingest-root mismatch. A real failure, a discovery failure, and a partially-blocked still-draining run are all unchanged. Queue-semantics only; the up-front whole-DAG composition check stays open in `docs/functional_requirements.md`.

## [0.5.11] - 2026-08-19
Minor, additive. Spreadsheet merge extents are captured and merge-covered
cells emitted; DOCX multi-row table headers are derived from `w:tblHeader`;
chunk document order is recoverable via `element_spans` +
`chunks_in_document_order`; the `DEFAULT-Isaacus` preset/config grow a fuller
reference shape; and `graph-refresh`'s in-place rewrite now commits atomically.
No parquet schema changed.

### Added
- **DOCX multi-row table headers emitted from `w:tblHeader`.** `DocxExtractor` (`ingest/strategies_file.py`) now derives a Word table's `header_rows` from the OOXML `w:tblHeader` ("repeat as header row at the top of each page") property via `_docx_header_rows`, taking the leading contiguous run of rows that carry it — so a genuine two-row hierarchical header (`Budget` over `$'000` / `%`) is emitted as `header_rows=[0, 1]` rather than collapsed to row 0 with the unit row read as data. The signal is *authored*, not a heuristic, so no header band is fabricated; a stray `w:tblHeader` deeper in the body does not fold data rows into the band, and a table with no declared header falls back to `[0]` (existing behaviour, every current DOCX fixture unaffected). Chips away at the Requirement 6 multi-row-header TO-DO: the spreadsheet producer (`_emit_sheet`) and the legacy `TableData` view (`views.py`) still emit a single header row, and no per-cell header-row coordinate is carried yet. Requirement 6 / 13 TO-DOs in `functional_requirements.md` updated.
- **Spreadsheet merge extents captured; merge-covered cells emitted.** `ingest/spreadsheet.py` gains a second, non-read-only openpyxl pass (`_read_merged_ranges`, separate from the streaming format pass so its bounded-memory profile is untouched) that maps each sheet's `ws.merged_cells`. A merge's openpyxl address (e.g. `"A1:C1"`) is annotated onto its top-left (anchor) cell's `merge_range`, and — the cascading half — every cell a merge covers is now emitted even when blank, since Excel leaves a merged region's covered cells empty and those blanks are structurally part of the merge. This makes a blank-anchored merge representable (the anchor cell now exists to carry the address) and keeps the merge's footprint visible downstream. Ordinary (non-merge) blank cells still stay absent; CSV keeps `merge_range` unset and emits no blanks. The new `sheet_cell` elements flow through `_sheets_to_table_data` into the table view / chunks and into `money_stage._sheet_rows`, where a covered blank is a null marker — excluded from `classify_column`'s numeric denominator but counted in `cells_total`/`null_fraction`, so a money column's audited verdict denominators shift while the verdict itself survives. On the current benchmark registers (AusTender, GrantConnect, SEIFA) no merge lands on the emitted data grid, so the effect is exercised by unit fixtures; SEIFA's header-band merges fall in the dropped preamble region. Requirement 6 / 13 TO-DOs in `functional_requirements.md` updated; `extraction.md` / `dataflow.md` cell descriptions updated.

### Changed
- **Chunk document order is recoverable: `element_spans` + `chunks_in_document_order`.** The `elem_order` anchor on table chunks (shipped 2026-08) could not actually be used. The recipe recorded alongside it — "sort narrative chunks by `start_char` and table chunks by `elem_order`" — gives two orderings in two incomparable key spaces; interleaving them needs the narrative offset each `elem_order` sits at, and nothing exposed one (`reassemble_narrative` returns only `page_breaks`, and chunks otherwise join to elements by offset overlap, never by `elem_order`). The anchor consequently had no consumer. `chunker.element_spans(elements)` now returns `(elem_order, start, end)` per narrative-bearing element — the offset map — and `chunker.chunks_in_document_order(rows, spans)` does the interleave: a table anchors where the element after it begins, sorting before a narrative chunk starting there (the table precedes that text in the document), one table's own chunks order by their offset into its markdown rather than by the order the rows arrived in, and spreadsheet sheets sort last, in arrival order — nothing in the chunks sidecar tells one sheet from another, so rows should be passed in `chunk_index` order. `element_spans` and `reassemble_narrative` are two views over one `_narrative_pieces` generator, so their coordinate space cannot drift. Ordering lives in the library, not in each consumer — the benchmark's document-order review spine (the ANAO/DFAT ground truth) must not derive an ordering of its own. No schema change, no offset shifts, no chunking change: the spans are read from the elements under the same `text_source` overlay the chunks were written under. The Chunk Inspector still renders in `chunk_index` order (all narrative, then all tables); wiring it needs a per-`source_hash` elements read on both the local and remote reader paths, and is a separate change.
- **`DEFAULT-Isaacus` preset and `configs/default-isaacus.yaml`: fuller reference shape.** The reference pipeline is now `extract → normalise → spellfix → enrich → chunk → build_graph → embed → money → link → done`. Three additions: **text cleaning runs first** — `processing.text_source: spellfix` selects the OCR-repaired layer (chaining on the normalised layer) as the single string both enrich and AI chunking reassemble from, which also puts `normalise` and `spellfix` into `enabled_downstream_stages` **before** `enrich` in `PIPELINE_ORDER` (`normalise` has no `enabled` flag — it is gated by a consumer selecting its layer); **`spellfix.enabled: true`** (Tier A digit→letter, en_AU); and **`linking.enabled: true`** for entity-register matching (the register is corpus-specific, so `linking.reference` stays the operator's to supply at run time — the config loads without it and the stage warns/no-ops until set). **AI chunking is unchanged** (`chunking.chunking_model: kanon-2-enricher`, already on) and still auto-wires `enrichment.persist_document` so chunk reuses the enrich Document. Preset overlay (`src/womblex/ui/presets.py`) and the config file are edited together and pinned by `test_config_file_and_ui_preset_agree` (now covering `spellfix`/`linking`/`text_source`). The vendored demo run is a subset of this shape, so its `{extract, chunk, enrich, embed, money}` assertion still holds; README's per-stage command sequence updated to 10 steps.

### Fixed
- **`graph-refresh`'s in-place rewrite commits atomically — an interrupted publish no longer leaves torn sidecars.** `graph-refresh` is the one `MutationMode.IN_PLACE` stage: it rewrites `*.enrichment_entities.parquet` and `*.graph_edges.parquet`, which already hold good bytes, and is never skipped — so a straight overwrite that failed between the two uploads could leave one sidecar rewritten against the other's stale bytes (or a half-written object) with no clean copy to fall back to. `stage_runner._publish` now forks on the contract's mutation mode: a `SIDECAR` stage still publishes straight to its live keys (its outputs are new siblings, so a torn publish self-heals under the all-or-none-plus-overwrite skip rule), while an `IN_PLACE` stage routes through the new `_publish_atomic`, which uploads every output to a temp key under `.staging` first and only once *all* have landed moves each onto its live key (`RemoteStore.move` — a server-side rename on S3, a rename locally). The slow, failure-prone uploads therefore touch only temp keys; the live keys change only in the fast move phase after every upload has succeeded, so a crash mid-upload leaves them untouched and orphans only temp objects (cleaned up best-effort). `.staging` is a leading-dot segment one level below the shard prefix, so discovery — which globs `<shard_prefix>/*.parquet` at the immediate level — never sees a staged temp object as a shard. Closes the Requirement 2 TO-DO in `functional_requirements.md` (acceptance criterion and TO-DO updated). No schema change; `SIDECAR` publish is byte-identical to before.

## [0.5.10] - 2026-08-19
Minor, additive. Headline fix: extraction now does only extraction —
`process_batch` no longer runs chunk/PII in-batch, where the output was
discarded, the order was wrong and a SageMaker client built mid-batch killed
whole runs. The downstream stages it displaced are now dispatchable: the job
queue carries stage rows, workers run them, and the console can press what it
composes. Two console defects fixed alongside (a Chunk Inspector empty state
that rendered over its own manifest read; the light-mode well colour). No
parquet schema changed; the `womblex_jobs` column addition is additive and
upgrades a live table in place.

### Added
- **The job queue carries downstream stage rows (issue 5, part 2, merge 1 of 2).** `womblex_jobs` gains a second row kind — `kind='batch'` (an extraction batch) | `'stage'` (one downstream stage over a whole run) — via additive `ADD COLUMN IF NOT EXISTS`, so a live deployment's table upgrades in place with its rows intact and nothing to migrate. `JobQueue.enqueue_stages(run_id, stages, shard_prefix)` writes one row per stage, idempotent on `(run_id, stage)`. Stage rows reuse `batch_num` as their queue position, offset past every real batch (`STAGE_SEQ_BASE`), so the existing `UNIQUE (run_id, batch_num)` gives that idempotency for free and `ORDER BY batch_num` drains extraction before any stage — no second ordering column and no constraint change. `claim` additionally holds a stage row until nothing earlier in its run is pending or running, so a fleet self-sequences `enrich → chunk → …` without a coordinator; batch rows keep claiming in parallel, and a *failed* predecessor settles rather than wedging the queue. `pipeline_order` gains `DOWNSTREAM_STAGES` + `enabled_downstream_stages(config)` — the stages a dispatcher may enqueue, config-gated per section (`normalise` follows the `text_source` that reads its overlay; `graph-refresh` only after AI chunking). **`pii` and `quality` are absent by design**: PII masking is irreversible and must not run because a flag was left on in a copied config, and `quality` is run-scoped — both stay reachable through `womblex run-stage`. Merge 2 has the worker run these rows.
- **Workers run the stage rows; `womblex enqueue-stages` dispatches them (issue 5, part 2, merge 2 of 2).** A worker claiming a `kind='stage'` row now calls `stage_runner.run_stage_remote` instead of `process_batch`, so execution stays on the fleet — a dispatcher (this CLI now, the console next) only ever writes rows, and retry, crash recovery, the batch log and one job list come along unchanged. `womblex enqueue-stages --run-id <id> --config <cfg>` queues the run's downstream stages, taking the list from `pipeline_order.enabled_downstream_stages(config)` and the ordering from `PIPELINE_ORDER` (`--stages` overrides the list, `--dry-run` prints it). Deliberately a separate press from `enqueue`: a worker will not start a stage until the run's batches settle, but a *bad* extraction should not spend Isaacus budget on enrich and embed either. New `stage_runner.prepare_stage_context` is shared with `cmd_run_stage`, so a queue-dispatched stage applies exactly the preflight/Isaacus checks the CLI does — without them `chunk_shards` warns, writes nothing and returns cleanly, which the queue would have recorded as a completed job. A non-zero stage summary fails its row rather than reading as done; stage checkpoints are staged in and out (the claim gate means no concurrent runner of the same run can clobber them), and the stage's log publishes to `runs/<run_id>/logs/stage-<name>.log` beside the batch logs.
- **The console dispatches the downstream stages it composes (issue 5, part 3).** `POST /api/execute/stages` plus a "Run downstream stages" card on the Pipeline Composer, below "Enqueue this run". The endpoint calls the same `enabled_downstream_stages(config)` gate and the same `JobQueue.enqueue_stages` that `womblex enqueue-stages` does, so a press writes rows byte-identical to the documented command — the console stays a skin over the CLI sequence and still only ever writes rows; workers read their own `--config` at launch. The config comes with the press (the composer's whole form state, built through the same `WomblexConfig` construction it validates and renders YAML with), so the stage list is the one the config *as the CLI would load it* asks for. Ingest is not required — stages read shards the store already holds, so a run whose ingest was since unset stays finishable — and a config enabling nothing is a 400 rather than an empty success. Which stages run is never decided in the frontend: re-deriving the list there would re-implement the gate (`normalise` answers to `processing.text_source`, `graph-refresh` to `chunking.chunking_model`), so the result panel reports what was dispatched, in claim order, instead of promising it up front. `pii` and `quality` remain undispatchable — that bound is `DOWNSTREAM_STAGES` on the server, so no request widens it. Dispatch is idempotent per `(run_id, stage)`.

### Fixed
- **Extraction does only extraction — `process_batch` no longer runs chunk/PII in-batch (issues 1 & 6).** `womblex.batch.process_batch` sequenced `extract → redact → chunk → pii`, gating chunk on `chunking.enabled` and PII on `pii.enabled`. But those flags now mean "this stage is in the pipeline", not "run it inside extraction"; the in-batch output was discarded (`write_results` has no chunk/clean_text path), it ran chunk *before* enrich (wrong order), and with `chunking_model: kanon-2-enricher` the in-batch chunk built a SageMaker client and raised `ValueError: No AWS region for SageMaker endpoint(s) …` mid-batch, killing every attempt. `process_batch` is now **extract → optional redaction detection** only — chunk, PII, enrich, embed, money are downstream `run-stage` contracts, dispatched separately. Redaction *detection* stays (it represents the source true-to-form, not a transform). No PII ever ran in-batch (both live runs had `pii.enabled: false`), so no masking or data loss occurred. `cmd_run`'s stage reporting and the now-moot `post_enrichment`-PII pre-flight guard are reconciled to match; a config that enables downstream stages logs a one-line "dispatch these per-stage after extraction" note instead. Cloud deployments must still set `ISAACUS_SAGEMAKER_REGION` (or `AWS_REGION`, or `…ENDPOINTS=…@region`) — the real enrich/chunk/embed stages call SageMaker; the software already surfaces the missing region correctly.
- **One declared pipeline order; the console no longer renders stages backwards (issue 5, part 1).** The order stages run in was written down three times and disagreed: `STAGE_CONTRACTS`'s dict order, `store/retention.STAGE_SUFFIXES` (commented "in pipeline order") and the README's command sequence. Both of the first two listed **chunk before enrich** — the reverse of the documented pipeline, where enrich must precede chunk so AI chunking reuses the enrichment — and the console rendered its lifecycle-checkpoint switcher and per-stage progress in that wrong order. New `womblex/pipeline_order.py` declares `PIPELINE_ORDER` once (with the two non-obvious edges reasoned at the site: the text overlays precede *both* their readers, and enrich precedes chunk); `STAGE_SUFFIXES` and the dashboard's `CHECKPOINT_DIRNAMES` are now sorted by it rather than hand-kept. Ordering stays out of `StageContract` deliberately — the enrich->chunk edge is config-derived (`chunk` reads `.enrichment_doc` only under `chunking.chunking_model`), so no topological sort over `required_inputs` recovers it.
- **Console: removed a dispatch capability it never had.** `ExecutionCapability.stages` served `STAGE_NAMES` over `GET /api/execute/status` and was typed in `api.ts`, reading beside `can_execute` as "the stages this console dispatches" — while no dispatch path for a downstream stage exists anywhere, and no caller ever read the field. Removed, along with the docstrings describing the same absent feature (`ui/execute.py`'s "the two write actions here — enqueue an extraction run, dispatch a downstream stage" and `ui/routes/execute.py`'s claim that per-stage dispatch is served by the Dashboard, which only reads checkpoints). Both now state plainly that the queue carries extraction batches only, so downstream stages remain the CLI's `womblex run-stage`. The pipeline's shape is still served, from the composer's `get_stage_graph()`, where it is derived from the contracts.
