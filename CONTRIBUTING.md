# Contributing to Womblex

<!-- Provisional: modelled on rbrasier/wayfinder's CONTRIBUTING.md; to be settled before 1.0. -->

Thanks for considering a contribution. Contributions are accepted under the
terms of the [Apache License 2.0](LICENSE).

Much of Womblex is built with AI coding agents, and
[`CLAUDE.md`](CLAUDE.md) is the working brief they follow: module
responsibilities, conventions and the things not to do. It applies to human
contributors in the same way.

---

## 1. Know where your change belongs

Read these before re-litigating a settled call or retrying a known dead end:

| Document | Holds |
|---|---|
| [`CLAUDE.md`](CLAUDE.md) | Module table, coding conventions, the size caps, what belongs in core |
| [`docs/decisions.md`](docs/decisions.md), [`docs/decisions-operations.md`](docs/decisions-operations.md) | Why things are the way they are |
| [`docs/decisions-dead-ends.md`](docs/decisions-dead-ends.md) | Approaches tried and abandoned |
| [`docs/functional_requirements.md`](docs/functional_requirements.md) | What Womblex must do |
| [`STABILITY.md`](STABILITY.md) | What may change between releases, and how breaking changes are announced |

## 2. Branch and merge

- Branch from `main` and open your pull request against `main`.
- **Pull requests are squash-merged.** Each merge lands on `main` as one
  commit, so the history reads one change per line. Write the PR title as the
  commit message it will become (see [Commit style](#commit-style)).
- A stacked PR is retargeted to `main` before it merges, never merged into its
  base branch.

## 3. Respect the shape of the codebase

The short version of `CLAUDE.md`:

- **Extraction is verbatim.** Text is what the producing extractor emitted; a
  wrong byte is fixed in the extractor, and cleanup is a downstream stage.
- **Each downstream stage writes its own sidecar** beside the extraction
  shards and never rewrites an earlier file.
- **No dataset-specific logic in core.** Dataset settings live in
  `configs/*.yaml`.
- **Open PDFs through the seam** (`womblex.ingest.pdf.open_document`); never
  import a PDF library elsewhere.
- **Size caps:** 750 lines per file, 500 changed lines per merge. Split a
  larger change into sequential merges that each pass on their own.
- **Dependencies:** a change to `pyproject.toml` dependencies needs maintainer
  approval and lands as its own merge, with `uv.lock` regenerated by `uv lock`.
- **Docs move with code:** a change that adds, moves or retires a module
  updates `docs/architecture.md` and `docs/project-structure.md` in the same PR,
  and a changed public name gets a [CHANGELOG](CHANGELOG.md) entry under
  `## [Unreleased]`.

## 4. Running checks

```bash
uv sync --extra dev --extra api
uv run ruff check src/ tests/
uv run mypy src/
uv run python -m pytest tests/ -v -m "not benchmark"
uv run --group docs mkdocs build --strict   # the API reference
```

CI runs all of them, and all must pass before a PR merges. The commit hook
(secret scan and the semgrep rules in `.semgrep/rules/`) installs with
`pip install pre-commit==4.6.1 && pre-commit install`; never bypass it with
`--no-verify`.

## 5. Opening a pull request

Every PR body follows
[`.github/pull_request_template.md`](.github/pull_request_template.md), which
GitHub pre-fills. For a non-trivial change the minimum is: **Summary**, **Task
and scope**, **What changed**, **Verification** (the exact commands and their
results), **Risk and impact notes** and the human review it needs. Say what
you did not verify rather than leaving it out.

## Commit style

[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```
feat(chunk): reuse persisted enrichment Documents for AI chunking
fix(ingest): accept OpenCV 5's HoughLinesP segment layout
docs(changelog): cut 0.6.0
chore(release): bump version to 0.6.0
```

Mark a breaking change with `!` (`feat(store)!: ...`) and a **Breaking:** entry
in the CHANGELOG.
